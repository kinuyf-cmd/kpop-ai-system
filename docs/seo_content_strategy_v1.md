# KPOP JOURNAL SEOコンテンツ戦略 v1（2026-05-25）

GSC 16ヶ月実測（21,401クエリ / 712,003 imp / 30,818 clicks）に基づく、**継続的に検索上位を取り続けるための生産の仕組み**。個別記事の指示ではなく、何を・いつ・どう作るかを判断するロジックを定義する。

---

## 1. 現状診断（数字で見た地形）

| テーマ | imp占有 | clk占有 | CTR | 性質 |
|---|---|---|---|---|
| ダンス番組(SWF3) | 16.7% | **35.4%** | **9.2%** | 稼ぎ頭。話題番組×網羅記事の勝ちパターン |
| 映画/アニメ(デーモンハンターズ) | 28.1% | 27.5% | 4.2% | 最大の畑 |
| 韓国ドラマ | 12.7% | 8.8% | 3.0% | imp多×CTR低=取りこぼし |
| トレンド商品(ラブブ) | 7.4% | 1.9% | 1.1% | 巨大需要・着手直後 |
| 美容/コスメ | 0.9% | 1.3% | **6.6%** | 小さいが高CTR=相性◎・未開拓 |
| 旅行/グルメ | 1.6% | 1.3% | 3.3% | 未開拓 |

**構造的事実:**
1. clicksの**71%が「話題の作品・番組」**（ドラマ/映画/サバイバル番組/トレンド）。→ バズった韓国コンテンツに素早く深い記事を当てると勝てる。
2. CTRが高いのに記事が薄い領域（美容6.6%・SWF3 9.2%）は「畑が小さいだけ」。広げれば伸びる。
3. impはあるが取れていない（ドラマ・ラブブ）はコンテンツの質量で改善可能。
4. **ビッグワード×強競合（例: BTS 聖地巡礼=57位）は新興ドメインに重い**。正面から狙わない。

## 2. 戦略の核心: 3レーンの生産モデル

単一軸でなく、性質の違う3つのレーンを**同時に回す仕組み**にする。

### レーンA: トレンド即応（攻め・最重要）
**話題化した韓国コンテンツに、話題化から数日以内に「網羅記事」を当てる。**
- 対象: 新ドラマ/映画/サバイバル番組/バズったトレンド商品。
- 当てる記事型（勝ちパターン）: **キャスト一覧・相関図・名前の読み方・楽曲一覧・メンバープロフィール**（SWF3/デーモンハンターズで実証済みの高CTR型）。
- なぜ勝てる: 競合が記事を出す前に1ページ目を取れる＝新興ドメインでも上位可能。clicksの71%はここ。
- トリガー源: 速報パイプライン(`breaking_news_detector`)が既に話題を検知している。**速報（短い第一報）→ 同テーマの網羅記事（深掘り）への昇格ロジックが欠けている**（§4の新規実装）。

### レーンB: ロングテール実用（守り・安定）
**「○○の使い方」「△△エリアの□□」など、競合が薄い実用クエリを厚く取る。**
- 対象: 美容(使い方/手順)、旅行(エリア×目的)、視聴方法、投票方法など。
- なぜ勝てる: ビッグワードを避け、検索意図が具体的なロングテールは新興でも上位可能（美容CTR6.6%が証拠）。
- 例: 明洞K-POPショップ巡り（7クエリが6-7位に集中）、メディキューブ美顔器の使い方。
- トリガー源: **GSCの「imp多×順位中位×CTR低」クエリ**を自動抽出（§4の新規実装）。

### レーンC: 既存資産の最適化（回収）
**imp はあるが順位中位の既存記事を、内容拡充・内部リンク・検索意図合致で1ページ目上位へ押し上げる。**
- 既存の `auto_rewriter` / `regeneration_queue_builder` / `winning_pattern_tracker` がこの守りを担う（実装済み）。
- 対象判定もGSC順位×CTRで自動化済み。レーンBの分析と共通基盤。

## 3. レーン横断の鉄則（品質・安全）

全レーン共通で、既存スキル群のゲートを通す。
- **3ペルソナ・ゲート**（初心者/コアファン/検索流入）+ 本文3000字 + H2≥3 + インラインstyle禁止。
- **事実は一次/権威ソースで裏取り**。検証できない固有情報は断定しない（kpop-original-article §7）。
- **ゴシップ・私的事実・未確認の噂は扱わない**（熱愛・脱退理由・解散経緯など。§7 + audit-rules）。
- **ビッグワード正面突破はしない**（強競合領域に新興ドメインのリソースを溶かさない）。
- 同一slugで再投稿しGSC資産を継承（消失記事回収で実証）。公開後はGSC Indexing API送信。

## 4. 仕組み化（欠けている司令塔）— SEO opportunity → 記事化キュー

現状、生産側（速報/引用/独自記事スキル）と守り（auto_rewriter）は揃うが、
**「GSC機会を検知して新規トピックをキューに積む司令塔」が無かった**（毎回手動分析していた）。
これを `lib/seo_opportunity_scanner.py` として**実装済み（2026-05-25、週次cron 月曜6:15）**:

1. **週次でGSC query次元を取得**（service_account / venv_kpi / 既存 fetch 経路を流用）。
2. クエリをテーマ分類し、各クエリを判定:
   - レーンB候補 = imp≥閾値 & 順位中位(4〜30) & CTR低 & 未記事化。
   - レーンC候補 = 既存記事に紐づくが順位中位 → auto_rewriter へ。
3. **除外フィルタ**: 自サイト指名検索（kジャーナル等）/ ゴシップ語 / ビッグワード強競合 / 既記事化テーマ。
4. 結果を `data/seo_opportunity_queue.json` に優先度付きで出力（potential = 上位化での追加click概算）。
5. owner/Claude がキュー上位を承認 → サブエージェント並列生成 → Claude検証 → 投稿 → Indexing。
6. レーンA（トレンド即応）は速報ログ（`breaking_news_detector`）の高engagementテーマを「網羅記事昇格候補」としてキューに合流。

→ これで「今後どんな記事を書くか」が**データdrivenに自動供給**され、毎回の手動分析が不要になる。

## 5. 運用カデンス（案）
- **週次**: opportunity_scanner 実行 → キュー更新 → 上位3〜5本を生成（並列）→ 検証 → 公開。
- **随時(レーンA)**: 速報で大型トレンド検知時、24-72h以内に網羅記事を昇格生成。
- **月次**: レーンCのリライト棚卸し（auto_rewriter の効果測定 = winning_pattern_tracker）。
- 効果計測: GSC順位/CTR/clicksの推移を `fetch_yesterday_metrics` + 本ドキュメントのKPIで追う。
