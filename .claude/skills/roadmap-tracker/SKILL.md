# Roadmap Tracker

## 1. 目的

長期ロードマップ(複数日〜数週間にわたる多項目の計画)の進捗を、
状態ファイルで一元管理し、朝・夜のバッチで可視化する。
達成/未達/遅延を毎日記録し、遅延を即座に検知して、
100点(完了)判定と改善タスク生成までを一貫して支援する。

「計画を立てる」だけで終わらせず、「毎日その計画がどれだけ進んだかを
正確に把握し、遅れたら気づく」ことがこのスキルの狙い。

## 2. 適用範囲

- **主用途**: KPOP JOURNAL 100点到達計画(16項目 A〜Q / 14日マイルストーン)
- **汎用用途**: 補助金プロジェクトなど、他の多項目・長期ロードマップにも
  同じ状態ファイル構造・報告フォーマットで適用できる。
- ロードマップごとに `roadmap_id` を変えて状態ファイルを分ければ、
  複数ロードマップを並行追跡できる。

## 5. 状態管理(JSON 構造)

進捗は単一の JSON 状態ファイル(§10 の保存先)で管理する。構造:

```json
{
  "roadmap_id": "kpop_100point_2026_05",
  "started_at": "2026-05-19",
  "target_completion": "2026-06-05",
  "current_day": 3,
  "milestones": [
    {
      "id": "M1",
      "day": 4,
      "items": ["A"],
      "status": "pending",
      "completion_pct": 0,
      "evidence": "/path/to/evidence.md"
    }
  ],
  "items": [
    {
      "code": "A",
      "name": "UI磨き",
      "milestone": "M1",
      "status": "pending",
      "skill_used": ["frontend-design", "ui-polish"],
      "blockers": []
    }
  ]
}
```

- `status` の取りうる値: `pending` / `in_progress` / `done` / `blocked` / `delayed`
- `completion_pct`: 0〜100 の整数
- `evidence`: 完了を裏づける成果物・レポートのパス。`done` 時は必須。
- `blockers`: ブロッカーの説明文字列の配列。空ならブロッカーなし。

状態ファイルを更新するときは、JSON 全体を読み込み → 該当フィールドを変更 →
書き戻す。壊れた JSON を書かないよう、書き込み後に必ず妥当性を確認する。

## 6. 朝バッチ報告フォーマット

朝バッチでは「今日これから何をするか」を明確にする。

```
## ロードマップ朝報告 — Day {N} / {roadmap_id}

### 対象マイルストーン
- {今日が属する Milestone ID と項目}

### 昨日の結果
- ✅ 完了: {昨日 done になった項目}
- ⚠️ 未達: {予定だが done にならなかった項目}

### 本日の着手項目
- {今日着手すべき項目コード・名前・担当}

### ブロッカー
- {blockers が非空の項目。なければ「なし」}
```

## 7. 夜バッチ報告フォーマット

夜バッチでは「今日何が進んだか」を記録し、状態ファイルを更新する。

```
## ロードマップ夜報告 — Day {N} / {roadmap_id}

### 本日 done になった項目
- {項目コード・名前 + evidence パス}

### 進捗更新
- {completion_pct を更新した項目とその数値}

### 遅延・ブロッカー検知
- {§8 の判定結果。delayed/blocked があればリカバリ案を添える}

### 翌日への申し送り
- {明日の着手項目・注意点}
```

夜バッチ実行時は、報告と同時に状態ファイル(§5)の
`status` / `completion_pct` / `evidence` / `current_day` を必ず更新する。

## 8. 遅延検知ルール(WARNING / CRITICAL)

毎回のバッチで全マイルストーン・全項目を走査し、次を判定する。

- **WARNING**: マイルストーンの予定日(`day`)を過ぎても `status` が
  `done` でない。または `blockers` が非空の項目が存在する。
  → 報告に明示し、リカバリ案(担当再配置・優先順位変更)を添える。
- **CRITICAL**: `blockers` が非空のまま48時間以上経過。または
  マイルストーン期日を2日以上超過して未完了。
  → 報告の冒頭に大きく出し、オーナー判断を仰ぐ事項として扱う。

遅延は「隠さず即報告」する。早期に気づくことがこのスキルの価値であり、
楽観的な見積りで遅延を `in_progress` のまま放置しない。

## 9. 100point-rubric-judge との連動

- 各項目の「完了」判定の質は、別スキル `100point-rubric-judge` に委ねる。
  本スキルは進捗の追跡、`100point-rubric-judge` は採点基準による合否判定。
- 項目を `done` にする前に `100point-rubric-judge` でルーブリック評価を行い、
  合格した場合のみ `status` を `done` にし、評価結果を `evidence` に記録する。
- **100点判定**: 全16項目(A〜Q)が `done` になった時点でロードマップ完了。
  最終的な「100点」認定は `100point-rubric-judge` の総合評価 +
  オーナーの目視・感性評価(CEO承認基準)をもって確定する。
  本スキルは「16項目すべて done」を機械的な前提条件として示すにとどめる。

## 10. 状態ファイル保存先

- KPOP JOURNAL 100点計画: `/home/aiuser/.kpop_recovery/roadmap_state.json`
- 他ロードマップ: `roadmap_id` を含む別ファイル名で同じディレクトリ、
  または各プロジェクトの作業ディレクトリ配下に置く。
- 状態ファイルは進捗の唯一の正本。複数の場所に進捗を散らさない。

## 11. 更新トリガー

状態ファイルを更新・参照すべき場面:

- 朝バッチ / 夜バッチの実行時(§6 / §7)
- 項目が `done` / `blocked` / `delayed` に変わったとき
- マイルストーンの日付・担当・完了基準が変わったとき
- オーナーから「今どこまで進んだ」「遅れている項目は」等の
  進捗問い合わせがあったとき(その場で状態ファイルを読んで答える)
- 新しいロードマップを開始するとき(新しい `roadmap_id` で初期化)

## 12. 出力ルール

- 進捗報告は §6 / §7 のフォーマットを守り、項目コード(A〜Q)を明示する。
- 推定値と実測値を区別する。Lighthouse スコア等を推定で書くときは
  「(推定)」と明記し、実測できるものは実測する。
- 遅延・ブロッカーは楽観的に丸めず、検知ルール(§8)どおりに報告する。
- 状態ファイルを書き換えたら、報告中にどのフィールドを更新したか述べる。
- このスキルは進捗の「追跡と可視化」に徹する。実作業や合否採点は
  各担当・各スキル(`100point-rubric-judge` 等)に委ね、二重管理しない。
