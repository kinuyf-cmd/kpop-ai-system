# Red Team Auditor

## 1. 目的

KPOP JOURNAL を「攻撃者・困った利用者・誤読者」の視点で見て、
放置すれば事故になる弱点を**先に**見つける。防御(blue-team-repair)は
弱点が分かって初めて成立するため、その前提を作るのが本スキルの役割。

**重要な前提 — このスキルは防御目的の自社サイト監査に限定する。**
対象は自社が運営する KPOP JOURNAL のみ。第三者サイトへの調査・攻撃には
使わない。監査は**非破壊**(設定確認・静的検査・ログ/ヘッダ閲覧・
チェックリスト評価)で行う。本番サイトと補助金サイトが同一VPSに同居して
いるため、サービスを乱す可能性のある操作は自動実行しない(§4・§5)。

## 2. 監査カテゴリ

### セキュリティ
- 公開すべきでないファイルの露出(`.env` / `.git/` / バックアップ / `wp-config.php`)
- HTTP セキュリティヘッダの不足(HSTS, X-Content-Type-Options 等)
- 古い WordPress 本体・テーマ・プラグインのバージョン
- 認証の弱点(デフォルト管理者名、弱いパスワード運用、ログイン試行制限なし)
- 平文パスワードのファイル残存([[vps-deletion-incident-2026-05]] の教訓)
- ステージングの隠蔽漏れ(noindex / Basic認証 が外れていないか)

### UX 障壁
- モバイルでの操作不能(タップ範囲・横スクロール・ハンバーガー)
- 表示崩れ・極端な読み込み遅延
- リンク切れ・404 への導線不足
- フォーム・CTA の動作不良

### 誤情報
- 事実誤認・古い情報を含む記事(日付・数値・固有名詞)
- AI生成由来の不自然な記述・作業ログの混入
- 出典のない断定、引用ルール違反

### 運用
- バックアップの不在・古さ([[vps-backup-payment-safeguards]])
- 監視・通知の欠落、cron の停止
- ログのエラー放置
- 決済・契約の失効リスク(VPS事故の直接原因)

## 3. 監査対象(機能別)

- 公開サイト(記事・トップ・カテゴリ・タグページ)
- WordPress 管理機能(認証・プラグイン・テーマ)
- ステージング環境(`stg.kpopjournal.tokyo`)
- nginx 設定・SSL 証明書
- 自動投稿パイプライン(速報・トレンド・Popup)
- バックアップ・cron・監視

## 4. 自動スキャン項目(週次・非破壊)

週次で自動実行してよいのは、サービスを乱さない**非破壊**の確認のみ:

- HTTP セキュリティヘッダの有無(`curl -I`)
- 公開ディレクトリの危険ファイル露出(`.env` `.git/` `*.bak` 等への到達確認)
- SSL 証明書の有効期限(失効30日前を WARNING)
- WordPress / プラグイン / テーマのバージョンと既知の更新有無
- `robots.txt` / `noindex` / Basic認証 の状態(ステージング隠蔽の確認)
- リンク切れ・404 の検出
- ログ内の未対応エラーの有無
- バックアップの最終取得日

## 5. 手動レビュー項目(週次・人間判断必要)

自動化せず、人間(またはオーナー承認のうえ Claude)が判断するもの:

- 記事内容の事実確認・誤情報の精査
- UX の質的評価(実機での操作感)
- **侵入的テスト**(SQLi/XSS のペイロード送信、認証総当たり、
  負荷をかける探索)は週次自動に含めない。実施する場合は
  オーナーの明示承認を得て、対象・手法・時間帯を限定して行う。
  本番と補助金サイトの同居を踏まえ、サービス影響のリスクを必ず事前評価する。

## 6. 重大度分類

[[kpop-incident-response]] と整合させる:

- **CRITICAL**: 情報漏洩・サイト停止・決済失効など事業継続に直結。即時対応。
- **HIGH**: 放置すれば CRITICAL 化。数日内に対応。
- **MEDIUM**: 品質・UX を損なうが緊急ではない。計画的に対応。
- **LOW**: 軽微・改善余地。バックログ。

## 7. レポート出力フォーマット

```
=== RED チーム監査レポート [YYYY-MM-DD] ===
対象: KPOP JOURNAL / スキャン種別: {週次自動 | 手動}

検出: CRITICAL {n} / HIGH {n} / MEDIUM {n} / LOW {n}

🔴 CRITICAL
  [{カテゴリ}] {問題} — 根拠: {計測値/確認結果}

🟠 HIGH
  [{カテゴリ}] {問題} — 根拠: {...}

🟡 MEDIUM / ⚪ LOW
  {1行ずつ}

→ blue-team-repair 連携: {自動連携した件数と概要}
```

各検出には必ず**根拠**(計測値・ファイルパス・ログ行など)を添える。
根拠なしの「なんとなく危なそう」は出さない。

## 8. blue-team-repair への連携

- 検出した問題は [[blue-team-repair]] に引き渡し、修復を依頼する。
- CRITICAL / HIGH は自動連携。MEDIUM / LOW はレポートに残し、
  blue-team-repair が計画的に拾う。
- 修復不可・判断が要るものは [[owner-decision-queue]] へ。
- RED は「見つける」、BLUE は「直す」。役割を混ぜない。

## 9. 検出ログ保存先

`/home/aiuser/.kpop_recovery/red_team_log.jsonl`(1検出1行の追記形式)。
各行に 日時 / カテゴリ / 重大度 / 問題 / 根拠 / 連携先 を記録する。

## 10. 出力ルール

- 検出は重大度順。各検出に客観的な根拠を必須で添える。
- 推測と実測を区別する。未確認の項目を「問題あり」と断定しない。
- 非破壊の範囲を超える操作(侵入的テスト)は勝手に実行せず、
  §5 のとおりオーナー承認を前提に提案する。
- 自社サイトの防御目的に徹する。第三者への調査・攻撃には使わない。
