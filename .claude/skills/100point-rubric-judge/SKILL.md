# 100-Point Rubric Judge

## 1. 目的

「だいたいOK」と「100点」の境界を客観化する。担当者の主観や楽観で
「終わった」と言うのではなく、ルーブリックの各チェック項目で
合否を判定し、数値で示す。

- 数値化できるもの(Lighthouse スコア等)は数値で判定する。
- 数値化が難しいもの(skill 完成、自動実行の動作)はチェックリストの
  合否で判定する。
- 「動いている」と「100点動いている」を区別する。1つ動いた程度で
  項目を満点にしない。

このスキルは採点に徹する。進捗の追跡は [[roadmap-tracker]] が担う。

## 3. 全体100点判定ロジック

- 全16項目 = 計 **63点満点**。
- **100点宣言の条件**: 各項目が満点の90%以上、かつ全項目が80%以上。
- **100点未達**: 1項目でも50%未満があれば未達。
- 1項目だけ未達でも「100点」とは言わない。100点は全項目が
  そろって高水準にある状態を指す。
- 機械的なルーブリック合格に加え、最終認定はオーナーの目視・
  感性評価(CEO承認基準)をもって確定する。本スキルはその
  前提条件としての客観スコアを提供する。

## 4. 判定実行(将来の Python 実装)

判定ロジックは将来 `100point_judge.py` として実装する想定。
インターフェース案:

- スコア入力: `--item A --score 4` (A項目を4/4に)
- 全体判定: `--all`
- レポート出力: `--report markdown`
- 状態ファイル: `/home/aiuser/.kpop_recovery/100point_state.json`

実装前は、状態ファイル(§8)を読んで本 SKILL.md のロジックに沿って
手動で集計・判定する。

## 5. 判定結果出力フォーマット

ALWAYS この形式で出す(30行以内・装飾最小・数値中心):

```
=== 100点到達計画 判定 [YYYY-MM-DD] ===
総合: {合計}/63 ({パーセント}%)
判定: {100点達成 | 100点未達(残り {差分}点)}

🟢 100点達成({件数}項目):
  {code}: {score}/{max} ★

🟡 80%以上({件数}項目):
  {code}: {score}/{max} ({pct}%) → 残り{差分}点

🔴 50%未満({件数}項目):
  {code}: {score}/{max} → 重点改善必要

📌 次の最優先: {code} ({項目名})
```

各バンド(🟢🟡🔴)に該当項目が無ければその節は省く。
80%以上だが90%未満の項目も🟡に含める(100点宣言には90%が必要)。

## 6. 改善タスク自動生成ルール

判定後、未達項目から次の方針でタスクを起こす:

- **50%未満**: 緊急タスクを作成し、[[owner-decision-queue]] へ連携。
- **80%未満**: 通常タスクを作成し、[[roadmap-tracker]] へ連携。
- **80%以上**: 完了見込み。残り点数と必要追加日数を算出して示す。

改善提案は1項目1行に収める(§9 出力ルール)。

## 7. roadmap-tracker との連動

- [[roadmap-tracker]] が項目を完了扱いにする前に、本スキルを
  自動呼び出ししてルーブリック評価を行う。
- ルーブリック score が満点(100%)に達した項目のみ、
  `roadmap_state.json` 側で `done` にしてよい。
- 全16項目が `done`(= 全項目ルーブリック満点)になったとき、
  「100点宣言」イベントを発火し、オーナーに通知する。
- 採点は本スキル、進捗追跡は roadmap-tracker。役割を二重化しない。

## 8. 状態ファイル

`/home/aiuser/.kpop_recovery/100point_state.json`

各項目の `score`(現在値)と `max`(満点)を保持する。
判定のたびに読み込み、スコア更新時に書き戻す。これが採点の唯一の正本。

## 9. 出力ルール

- 判定結果は **30行以内**、装飾は最小限、数値中心。
- 改善提案は **1項目1行のみ**。詳細な改善手順は要求されたときだけ出す。
- 推定スコアと実測スコアを区別する。Lighthouse 等を未計測のまま
  推定で埋めない。未計測の項目は未達(`[ ]`)として扱う。
- 「だいたい」「ほぼ」で項目を満点にしない。チェック項目の合否は
  客観的な根拠(計測値・動作確認)に基づく。
